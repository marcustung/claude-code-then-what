# 驗收草稿（依 spec.md v1，未實作）

## 1. 需求來源
- 工單 ORD-142，v1，全部內容（僅一句）：「讓使用者可以取消尚未出貨的訂單。」
- 無其他章節、無驗收條件、無錯誤處理說明。

## 2. 已明示的行為與具體情境

| 情境 | 已明示行為 |
|---|---|
| 訂單 `Shipped = false`（尚未出貨） | 可以取消 |

僅此一條為明示行為。其餘欄位（`Paid`、`Cancelled`）及回傳值（`RefundRequested`）皆未在需求句中提及，僅出現在程式骨架中。

## 3. 尚未明示、但會改變實作或驗收結果的問題（推論／待確認，皆標示）

1. **已出貨（`Shipped = true`）時呼叫 `Cancel`，應如何處理？**
   - 未明示。可能選項：拋例外／回傳原樣不變的 `Order`／回傳但標記失敗（但 `CancellationResult` 無 success/failure 欄位可用）。
   - 影響：決定回傳型別是否足夠表達「取消失敗」，甚至可能需要改變 `CancellationResult` 結構——但簽名已鎖定不可改，這會限制可行方案。

2. **`RefundRequested` 的判定規則是什麼？**
   - 骨架顯示這是回傳值之一，但需求句完全未提「退款」。
   - 推論：可能與 `Paid` 欄位相關（已付款且取消 → 需要退款旗標為 true；未付款 → false）。此為**推論**，非需求明示。
   - 執行限制寫明「不執行退款，`RefundRequested` 只是記憶體旗標」，這確認了「不會真的退款」，但沒說旗標**該在什麼條件下**設為 true。

3. **已被取消過的訂單（`Cancelled = true`）再次呼叫 `Cancel`，應如何處理？**
   - 未明示。是否視為冪等（回傳相同結果）、或視為錯誤情境。

4. **回傳的 `Order` 內容為何？**
   - 是否要回傳一個 `Cancelled = true` 的新 `Order`？`Shipped`、`Paid` 是否原樣保留？
   - 需求未描述輸出資料的具體內容，僅描述「可以取消」這個動作允許發生。

5. **未付款（`Paid = false`）的訂單可否取消？**
   - 需求僅以「尚未出貨」為條件，未提付款狀態是否影響可否取消。是否隱含「只要沒出貨就都能取消，不論付款」？此為推論，未經明示。

## 4. 建議確認角色

| 問題 | 建議角色 |
|---|---|
| 已出貨時的行為（例外 vs 其他） | 待指定（需求提出方或負責錯誤處理慣例的工程負責人） |
| `RefundRequested` 判定規則 | 需求提出方（工單負責人），因涉及業務邏輯（退款觸發條件） |
| 已取消訂單重複取消的行為 | 待指定 |
| 回傳 `Order` 內容規則 | 待指定 |
| 未付款訂單是否可取消 | 需求提出方 |

## 5. 確認後可用的驗證方式

- 針對每個明示/待確認情境，各補一組單元測試輸入（`Shipped`/`Paid`/`Cancelled` 的組合）與期望輸出（回傳的 `Order` 內容、`RefundRequested` 值，或是否拋例外／例外型別）。
- 因執行限制禁止外部副作用，驗證僅需在記憶體中比對輸入輸出即可，不需要 mock 外部服務。

## 受阻範圍
在問題 1（已出貨行為）與問題 2（`RefundRequested` 規則）確認前，`Cancellation.Cancel` 的核心邏輯與回傳值皆無法定案，**整個方法實作會被阻擋**。問題 3～5 影響邊界情境的正確性，但不阻擋主流程（尚未出貨且未取消訂單的正常取消路徑）的最小實作。
