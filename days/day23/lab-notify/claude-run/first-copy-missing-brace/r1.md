# 通知漏送調查：run-a（只讀，未改任何檔案）

## 結論

**有 6 則通知被取走後丟棄，從未送出。** 9 次成功取消只有 3 則抵達接收端（`receipts.jsonl` 3 行）。`oc_notify_sent_total=9` 這個數字不可信，因為它在「延後」分支也被加 1。Log 沒有 ERROR，是因為延後被記成 `INFO notify_deferred`，而且沒有任何地方會重新處理它。

## 一、依事件追蹤：API 接受之後各分支的結局

以 `run-a-r001`（o-01）為例，這是最先被漏掉的一筆：

1. `Program.cs:63-65`：建立 Notification，寫入 channel，`enqueued +1`。
2. `Program.cs:140`：worker 取出，等 `DelayMs`（`:142`）。
3. `Program.cs:143-147`：`queue.Count > QueueLimit`，進入延後分支。
   - 記 `notify_deferred`（log 第 16 行，id `adb413f7…`）。
   - 執行 `continue`，不 POST、不重新入列、不排程重試、不進 dead_letter。
4. 這個 id 後面沒有 `notify_sent`，接收端也沒有收據。

整輪 9 筆轉換的最終狀態：

| 分支 | 事件 | 結局 |
|---|---|---|
| 完成 | r013 o-09、r014 o-10、r015 o-11 | log `notify_sent`（log 第 28-30 行）和收據都有，一一對得上 |
| **丟失（延後後無人處理）** | r001 o-01、r002 o-02、r004 o-04、r006 o-05、r008 o-07、r010 o-08 | 只有 `notify_deferred`（log 第 16、23-27 行），之後無任何紀錄 |

| 失敗／dead_letter | 無 | 無 `notify_attempt_failed`、無 `notify_dead_letter` |

- 6 個丟失的通知 ID 依序是：`adb413f7…`、`cba06e3d…`、`bf6ab2fc…`、`f9277350…`、`252109d8…`、`129fb176…`。
- 其中 r002、r004、r008 是 `refund_requested=true`，也就是已付款的使用者沒被通知退款。
- **重新執行的位置：沒有。** 我查了整個 `src/`：worker 只在 `Program.cs:140` 從 channel 讀取。`channel.Writer` 只在 `:64` 被呼叫，且是 API 端的唯一一次。HTTP 重試迴圈（`:149-163`）只涵蓋 POST 失敗，不涵蓋延後分支。

## 四、分開看：已確認、原因假設、缺少的來源

**已確認（有檔案與行號佐證）**
- 6 則 `notify_deferred` 後沒有任何後續處理，其餘 3 則正常送達。
- `notify_sent_total=9` 由延後分支和真送共同累加（6+3，與 log 筆數吻合）。
- 沒有任何程式路徑重新處理延後的通知。
- `FakeSink` 的收據是獨立寫的，3 行與服務 `notify_sent` log 的 3 行 ID 完全一致。

**原因假設（未被直接證實）**
- 延後是由 `notify_queue_limit` 與 `notify_delay_ms` 旗標觸發。我從 log 反推約 `limit=2`、`delay≈400ms`（延後記錄間隔約 400 ms，queue_depth 降到 2 才開始真送）。這是反推，不是讀到旗標檔。
- 這是為「佇列壅塞」情境設計的故障注入，不是營運常態；真實流量是否打開了這個旗標，這份資料看不出來。

**缺少的來源**
- `OC_FLAGS` 旗標檔不在 `run/`，無法確認實際限制值。
- **`Program.cs:143-147` 寫成 `if (…)` 後接多行但沒有 `{`，而 `:147` 有 `}`，大括號不平衡，照現在的檔案應該編不過。** 且 `manifest.api_sha256`（`E04A2347…`）與目前檔案的 SHA256（`A695C65F…`）不同。所以：
  - 我讀到的 `Program.cs` 不是這一輪跑的版本，或雜湊算法不同，我無法判斷是哪種。
  - 上面的行為結論來自 log 與計數器的互相吻合，原始碼證據只能算「與 log 一致的推測」。
  - 我沒有執行 `dotnet build`，以避免產生 bin/obj。
- 沒有 GET 請求紀錄，`requests.jsonl` 只有 cancel；NC-04 的「狀態已改」層只能靠 cancel 回應裡的 `order.cancelled`，沒有獨立讀取。
- `tests/` 只有 Domain 測試，沒有任何通知、佇列或收據相關的測試。
