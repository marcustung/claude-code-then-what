# 調查結果：run-a 取消通知「全部送出」但只有 3/9 送達

唯讀調查，未修改任何檔案。run-a 九筆成功轉換中，只有 3 筆有接收端收據；另外 6 筆在 worker 被標成「延後」後直接丟棄，沒有重新入佇列。`notify_sent_total` 卻把這 6 筆也算成「已送出」。

**每個分支的最終狀態**

- 「送出」分支：完成，有 3 筆收據佐證。
- 「重試/dead_letter」分支：本輪沒有觸發。沒有任何 `notify_attempt_failed` 或 `notify_dead_letter`，所以沒有 ERROR。
- 「延後」分支：**既不完成、不等待，也不失敗，而是消失**。
  - 位置在 `src/Api/Program.cs:143-147`：log 一行 INFO 後直接 `continue`。
  - 該則通知已被 `ReadAllAsync` 取出，全檔唯一的 `channel.Writer.WriteAsync` 在 `Program.cs:64`（API 入佇列）。
  - 因此延後後**沒有任何地方會重新執行**，也沒有 timer、重新入佇列或持久化。
  - 這個分支也不在契約內：NC-05 只定義「重試 → dead_letter」，沒有「延後」。

**對帳等式（契約第 26 行）**：轉換 9 == enqueued 9，但 receipts 去重後只有 3，所以 FAIL。`manifest.json` 的 `expected.notifications_received` 是 9，實際是 3。

**manifest 把這輪標成 `terminal`**：判準是「queue_depth==0 且 receipts 穩定 3 次輪詢」。丟棄的通知讓佇列歸零，收據自然穩定，所以判準在漏送時一樣會成立。`manifest.json` 沒有任何欄位拿 `expected` 去比對實際值。

## 三、原因假設（有證據但不是直接證明）

1. **延後是旗標驅動**：log 的 `startup` 寫 `flags_loaded:true`。`RuntimeFlags` 有 `notify_delay_ms` 和 `notify_queue_limit`。
   - 延後事件間隔約 0.4 秒，推測 `notify_delay_ms` 約 400。
   - o-08 延後時深度是 3、o-09 送出時深度是 2，推測 `notify_queue_limit` 是 2。
   - 這兩個數字都是推算，旗標檔不在 `run/`。
2. **正式環境的漏送是否同一機制，不能確定**：同樣的「積壓 + 延後設定」是否存在於維運環境，需要看當時的旗標。
3. **「延後」疑似原本想做背壓或限流**，但沒寫完重新排程。`:143-147` 少了 `{`，這是推測。

## 四、缺少的來源

- **旗標檔**（`OC_FLAGS` 指向的檔案）：無法證實 delay 和 limit 的實際值。
- **磁碟上的 `Program.cs` 與實際跑的版本不一致**：`Program.cs:143-145` 的 `if` 缺左大括號，照現狀無法編譯（我沒有跑 `dotnet build` 驗證，只是閱讀判斷）。
  - 實際執行的 binary 必然是另一份。metrics 的 9 = 6 + 3 只有在 `{` 存在時才成立。
  - `manifest.json` 的 `api_sha256`（E04A…）與我算的 `Program.cs` SHA256（a695…）不同。manifest 雜湊的對象不明，不能直接當作「原始碼被改過」的證據。
  - 因此第一步要先取得實際執行版本的原始碼，再下結論。

- **跑本輪的驅動腳本**（產生 manifest 與等待判準的程式）：不在工作區。
- **維運回報的實際訂單與使用者**：沒有提供，無法對回這 6 筆。
- 我只確認 `tests/` 中沒有出現通知相關字串；沒有逐檔閱讀，所以不宣稱測試覆蓋情況。

## 五、建議修改（尚未動手）

**要改的分支**：`NotificationWorker` 的「延後」分支（`Program.cs:143-147`）。

1. **先決定語意**：延後只能是「晚一點再送」，必須最終走到送出或 dead_letter。做法二選一：
   - 簡單版：移除這個分支，只保留 `notify_delay_ms` 當作送前延遲。
   - 保留限流版：延後時重新入佇列（帶 `deferred_count` 與上限），超過上限進 dead_letter。
2. **修正計數器**：`notify_sent_total` 只在 `:166`（POST 成功）增加，刪掉 `:144` 那次。
3. **補訊號**：
   - 新增 `oc_notify_deferred_total`，以及延後件數的 gauge（或讓 `queue_depth` 包含待重送件）。
   - `notify_deferred` 事件補 `deferred_count`、`next_attempt_at`。
   - 若延後超過上限，記 ERROR `notify_dead_letter` 並附 `reason="deferred_exhausted"`。
4. **補收尾判準**：驅動腳本要用「receipts 去重數 == transitions」判定 terminal，而不是只看 `queue_depth==0`。`manifest.json` 要寫出 `expected` 與 `actual` 的比對與 pass/fail。

**驗收**

- **故障重跑**：用同一份 run-a 劇本，帶相同的 delay/limit 旗標（需要先取得原旗標檔）。
  - 預期 transitions 9 == enqueued 9 == receipts 9。
  - `notify_sent_total` 等於 receipts 數。
  - 延後的通知最終都有 `notify_sent` 事件，或者進 dead_letter 並帶 ERROR。
  - 修改前的程式在同一重跑下，會因為 receipts 3 ≠ 9 而被判 FAIL。這次重跑要能證明對帳判準抓得到漏送。
- **正常回歸**：不帶旗標重跑 run-a，結果要與原先一致（9/9/9，refund true 5、`dead_letter` 0）。同時加一個「接收端暫時回 500」的場景，驗證 NC-05 的 200/400/800 ms 重試與 dead_letter 仍有效。

這次調查的結論（延後分支丟件、sent 計數灌水、terminal 判準失效）值得存起來，可用 `/brain-save` 存入大腦。
