# 調查結果：9 筆通知只有 3 筆送達，其餘 6 筆被 worker 丟棄，但 `notify_sent_total` 仍計 9

Brain 的 `INDEX.md` 沒有相關筆記，以下只依本次 workspace 的檔案。

## 結論

這一輪 9 筆成功轉換都進了佇列，但只有 3 筆（o-09、o-10、o-11）被送到接收端。

另外 6 筆被 worker 標為 `notify_deferred`，之後沒有任何程式把它們重新放回佇列。這 6 筆既沒有送出、沒有重試，也沒有進 dead_letter。

`oc_notify_sent_total` 在「延後」分支也 +1，所以 metrics 顯示 9。這個分支只寫 INFO log，沒有 ERROR。

## 已確認的事

- 9 筆通知入佇列。
- 3 筆有 `notify_sent`，且接收端收據與之對得上。
- 6 筆是 `notify_deferred`，沒有後續動作，也沒有收據。
- `metrics.txt` 的 `sent=9` 與收據 3 筆矛盾。
- `manifest.json` 的 `status: "terminal"` 與 `expected.notifications_received: 9` 並存，但實際收據只有 3。
- `manifest.json` 的終止條件是 `queue_depth == 0` 且收據連續 3 次輪詢不變。佇列被「丟棄」排空也滿足這個條件，所以這個條件沒擋住問題。

## 原因假設（尚未證實）

1. `notify_queue_limit` 和 `notify_delay_ms` 是故障注入旗標。
   - `startup` log 有 `flags_loaded:true`，但旗標檔不在 `run/`。
   - 從 depth 變化推測 limit 約為 2、delay 約 400 ms：延後事件的 depth 是 7、7、6、5、4、3，而第一筆被送出時剩 2。
   - 這是推測，不是已確認。
2. 「超過佇列上限就延後」的設計意圖可能是背壓，但實作只做了「略過並計數」，沒做「稍後重做」。
3. `sent_total` 在延後分支 +1，可能是為了讓 metrics 看起來完成，也可能是誤寫。程式沒有註解說明，無法判斷是有意還是失誤。

## 缺少的來源

- 旗標檔（`OC_FLAGS`）的實際內容。
- 本輪執行的場景檔與 runner 腳本。
- 取消後的 `GET /orders/{id}` 紀錄，無法確認 NC-04 第二層「狀態已改」。
- `run-a` 是測試場景（`manifest.json` 寫 `scenario: run-a`），不是營運環境。維運回報的實際事件的 log 與 metrics 未提供。我無法證明營運事故與這輪是同一個原因，只能證明這輪重現了同一現象。

## 建議修改（先不動程式）

### 要改的分支
`Program.cs:143-148` 的延後分支。

### 修改方向
1. 延後不能計 `sent`。改成：
   - 重新入佇列，帶 `deferred_count`、設上限，或延遲後重送。
   - 超過上限時，走與 `Program.cs:170-174` 相同的 dead_letter 路徑。
2. 把 `Program.cs:145` 的 `notify_sent_total` 刪掉。
3. 只有 HTTP 2xx 才增加 `notify_sent_total`。

### 要補的訊號
- `oc_notify_deferred_total`、`oc_notify_requeued_total`。
- 所有計數器啟動時就輸出 0。
- 服務端在 `/metrics` 增加「已入佇列但尚未終態」的數量，也就是 `enqueued - sent - dead_letter`。
- runner 的 terminal 條件要加一條：`receipts 去重數 == transitions`，不再只看佇列為 0。

### 驗收
- **故障重跑**：用同一份旗標（limit 約 2、delay 約 400 ms）、同一場景重跑。
  - 預期 `receipts` 去重 = 9，或 `receipts + dead_letter = 9`。
  - 每個 `notification_id` 都能在 receipts 或 dead_letter log 中找到。
  - `sent_total` 等於收據數。
  - 若任何一筆在 receipts 與 dead_letter 都找不到，必須判 FAIL。
- **正常回歸**：不帶旗標重跑 run-a。
  - 轉換 9 == enqueued 9 == receipts 9。
  - 冪等 6、已出貨 3、not_found 1、unauthorized 1 與 `expected` 一致。
  - `deferred_total` 為 0，`dead_letter_total` 為 0。
- **沒有故障注入的重試路徑**：讓接收端暫時回 500，確認 200／400／800 ms 重試與上限，以及 dead_letter 計數與 `ERROR` log。
