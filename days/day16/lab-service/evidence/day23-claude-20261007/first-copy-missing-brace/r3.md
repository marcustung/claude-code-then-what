# 取消通知漏送：根因在 `notify_deferred` 分支

**結論：** 這一輪 9 筆成功取消各入佇列一則通知，接收端只收到 3 則，其餘 6 則被 worker 以 `notify_deferred` 丟棄，沒有重新執行的程式碼。同時 `oc_notify_sent_total` 在丟棄時被加 1，所以 metrics 顯示 9/9。Log 沒有 ERROR，是因為這個分支只寫 INFO，也不計入 failed 或 dead_letter。

大腦（`Brain\INDEX.md`）查無相關筆記，以下全部依本次 workspace 檔案判斷。

## 一、事件沿線結果

API 接受之後，每筆事件經過的分支如下（程式位置在 `src/Api/Program.cs`）：

| 取消成功且 transitioned（`:57`、`:60-66`） | 9 筆：r001、r002、r004、r006、r008、r010、r013、r014、r015 | 入佇列，`enqueued=9` |

## 二、「延後」實際會在哪裡重新執行？

答案是沒有。

- `Writer.WriteAsync` 全檔只有 `:64` 一處，也就是 API 入佇列。
- `:143-147` 的分支寫完 log 後 `continue`，沒有回寫 channel、沒有排程、沒有 timer。
- 全檔沒有第二個消費者，也沒有補送機制。

所以「延後」其實是「丟棄」，沒有對應的重新執行位置。

## 五、分開列：已確認、假設、缺少的來源

**已確認（有檔案或事件為證）**
- 3 則送達，6 則丟棄，6 則的 id 與 request 對應如上表。
- 丟棄後沒有任何重新執行，這是程式結構決定的（`:64` 是唯一的入佇列點）。
- `sent` 計數器在 `:144` 被誤加。
- Log 無 ERROR（`"level":"ERROR"` 計數為 0）。
- `manifest` 把「queue 排乾」當成 terminal，沒有核對 `receipts` 是否達到 expected。

**原因假設（無直接證據）**
- 丟棄的觸發條件應是 `notify_queue_limit≈2` 與 `notify_delay_ms≈400`。依據是 `startup` 的 `flags_loaded:true`、每則約 400 ms 的間隔，以及 depth ≥3 時丟棄、o-09 在 depth 2 時送出。

**缺少的來源**
- 本輪 `OC_FLAGS` 檔案內容，workspace 找不到。
- **原始碼與實際執行檔不一致。** `src/Api/Program.cs:143-144` 的 `if` 缺少 `{`，照現在這份檔案無法編譯，但 log 證明執行檔有 deferred 分支。`manifest.json` 的 `api_sha256`（`E04A2347…`）與目前檔案 SHA256（`a695c65f…`）也不同。我無法確認 `api_sha256` 雜湊的對象（原始碼或建置產物），所以不能斷定哪一份是跑過的版本。
- 沒有 `GET /orders/{id}` 的紀錄。
- 沒有 sink 失敗的故障輪，因此 NC-05 的重試與 dead_letter 從未被實際驗證。
- 真實使用者回報的訂單 ID。我只能證明本輪的 6 筆確實未送達，不能證明回報者就是這 6 位。

## 六、修改建議（尚未動手）

**改哪個分支：** `Program.cs:143-147` 的 deferred 分支。

1. 不要 `continue` 丟棄。把它改成真正的背壓：只延後處理（例如把 `n` 放回佇列尾端或延後重排），並且有明確的重新執行位置。如果決定放棄這個行為，就整段刪除。
2. 刪除 `:144` 的 `notify_sent_total`。
3. 補訊號：
   - `oc_notify_deferred_total` 與 `oc_notify_pending` gauge。
   - 若確定放棄，必須走 dead_letter 並寫 ERROR 或 WARN，符合 NC-05。
   - `Render` 啟動時把各計數器預設輸出 0。
4. 補 run 的終態判定：`manifest` 的 terminal 條件加上 `receipts == expected.notifications_received`，不符就標 FAIL，不能標 terminal。
5. 修好 `:143-144` 的括號，並讓 manifest 的 `api_sha256` 對應到明確的檔案。

**驗收：**
- **故障重跑：** 用同一份 flags（queue limit 2、delay 400 ms）重跑 run-a。預期 `enqueued = receipts（去重）= 9`，丟棄分支不再造成缺口；若保留丟棄，則 `dead_letter=6` 且 `sent=3`，對帳等式明確 FAIL。
- **sink 故障輪：** 讓 sink 回 500，確認出現 3 次重試（200/400/800 ms）後進 dead_letter、有 ERROR log、`sent` 不增加。
- **正常回歸：** 無 flags 重跑 run-a，維持 `transitions 9 / enqueued 9 / receipts 9 / idempotent 6 / rejected 3 / refund true 5`，且 `sent == receipts`。
- 另外補一次 `GET /orders/{id}` 紀錄，涵蓋「狀態已改」那一層。
