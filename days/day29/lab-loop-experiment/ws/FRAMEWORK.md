# cs-loop 治理框架憲法（FRAMEWORK.md）

> **框架本身的單一事實來源（SSOT）。** 三件套治理「一個 repo」；本文件治理
> 「框架自己」——分層模型、判準、生命週期、修訂規則。
> 正本只放在工具 repo（loopdeck/templates/），**不隨骨架複製到各 repo**，
> 避免框架版本在實例間漂移；各實例以「引用」方式遵循。
>
> 狀態：**v1**（2026-07-12）｜修訂規則見 §7，版本表見文末。

---

## 1. 分層模型（框架的第一原理）

```
憲法層｜治理三件套     — SSOT（為何存在）・Evolution_Goals（往哪去）・Stability_Goals（不能壞什麼）
執行層｜八步例行       — .claude/commands/cs-loop.md：步驟、鐵律、去重節流、紅線觸發
心跳層｜排程           — 本機工作排程器或雲端 routine：只決定「何時跑」，不含治理內容
觀測層｜LoopDeck       — 裁決、審核、趨勢、排程狀態：是視窗不是資料庫
```

- 各層獨立演化：換心跳不動三件套；改北極星不用重建排程。
- 排程 prompt 是純觸發器——**只引用 repo 內文件，不複述步驟與鐵律**（防事實分裂）。
- 觀測層不得成為第二事實來源：迴路的真相在 repo、排程的真相在排程器。

## 2. 新迴路啟動：MVG 四項硬前置

缺一不啟動排程（缺了會造成方向錯誤或安全風險）：

1. **北極星一句話**（SSOT §1.1）——提案的對映基準
2. **3-5 個 outcome 型輸入指標＋黃紅線**（Evolution §1.1）——不可用活動量冒充；
   尚不可量測就誠實標註（生成真實性）
3. **不可觸碰清單**（Stability §4）——安全邊界
4. **雙 Gate 權限宣告**——誰核准（裁決欄）、誰合併

可邊跑邊長：價值鏈完整拆解、指標補齊、六大穩定性 KPI 完整對映、回寫規則細化。
建立順序固定為：憲法層 → 執行層 → 心跳層 → 觀測層註冊。

## 3. 排程（心跳）判準

同一迴路要加新心跳，三個條件**命中任一**才正當：

1. **節奏不同**——任務的資訊變化速度與現有例行不合拍（每日 vs 每週 vs 每月）
2. **權限邊界不同**——一個排程一組最小權限白名單；唯讀任務不拿寫碼權
   （觀測來源是外部輸入，白名單決定 prompt injection 的爆炸半徑）
3. **失敗隔離**——長任務或易掛任務不得拖垮主迴路

反面清單：想多觀測一個東西 → 改觀測步驟；想立刻跑一次 → 手動觸發；
一次性任務 → 不排程。**經驗上限：一個迴路 1-3 個心跳**，超過即懷疑例行設計太碎。
本機 vs 雲端選型：產出要先過人的手（本地閉環）→ 本機；產出直接對外、機器不保證
開著 → 雲端。

## 4. 治理範疇判準

**資產三問**（決定一個產出物入不入治理範疇）：

1. 會留在 repo 嗎？
2. 需要跟著 code／產品演化嗎？
3. 壞掉（過期、與現實不符）會有人受害嗎？

三個 yes → 治理資產，入迴路；有 no → 一次性任務，session 做完即結束。
灰色地帶：先當一次性做，被反覆引用時再補案納管——資產身分由使用證明。

**三系統邊界**：

```
cs-loop（治理殼）  ：決定要不要做、優先序、驗收、壞了誰負責——管資產的一生
生產引擎（skills） ：實際產出 code/規格/文件——被治理殼呼叫，不自己決定做什麼
一次性 session     ：不留資產的工作——在殼外，零治理成本
```

## 5. 成效判讀（三層）與 framework tax

- **每天**：outcome 輸入指標 vs 黃紅線（線遠離紅線＝變好）
- **每案**：覆盤比對「實際指標變化 vs 提案預期」——提案有效性有數據答案
- **每月**：迴路自身健康——提案通過率、消化率、MVG 完整性

**framework tax 門檻**：治理成本（裁決、回寫、憲法維護）只在 AI 代勞量夠大時划算。
啟發式：預期 routine 每週產出 **≥3 件**值得裁決的提案、或 repo 有稽核／多人協作
需求，才掛迴路；低於門檻用一次性 session＋生產引擎即可。

## 6. 迴路生命週期（管生也管死）

| 階段 | 觸發條件 | 動作 |
| --- | --- | --- |
| **降頻** | 輸入指標連續 4 輪全綠 且 新提案連續 4 輪 = 0 | 心跳降頻（每日→每週）；LoopDeck 排程欄註記；指標轉黃紅或積壓出現即恢復 |
| **暫停** | 產品凍結／團隊暫離 | 停用排程（不刪）；backlog 凍結；恢復時先跑一輪完整觀測 |
| **退役** | 產品 EOL，或 backlog 連續 4 週零活動且無恢復計畫 | ① routine 產出「最後覆盤總結」（迴路一生的指標變化與未竟提案）② governance/ 加 `ARCHIVED` 標記 ③ 刪排程 ④ loops.json 移除 ⑤ 治理資產隨 repo 歸檔，不刪除 |
| **合併** | 兩迴路的提案高度相依、裁決人相同 | 三件套合併（北極星必須真的可合一，否則不合）；backlog 併單；心跳擇一 |

## 7. 框架自身的修訂規則（元治理）

- 框架修訂比照治理文件：**提案（FW-ID）→ 人類裁決 → 修改本文件 → 版本表記錄**。
  有 diff 無版本記錄＝違規（框架適用自己的透明性鐵律）。
- **回流義務**：框架修訂被核准後，7 日內回流所有運行實例（templates 骨架＋各 repo
  的例行檔）；未回流的實例視為框架分裂，列入下輪觀測。
- **判準偏差累積**（框架演化的訊號來源）：每輪覆盤統計「人類裁決 vs AI 預判」的
  偏差並記入 health report 迴路健康段；**同型偏差累積 ≥3 次 → routine 自動開一筆
  判準修訂提案**（修 Triage 判準或本文件），過人類裁決後生效。
- 過早固化也是框架債：修訂提案須附「訊號證據」（哪個實例、哪幾輪、什麼偏差），
  無訊號的「理論上該有」不收。
