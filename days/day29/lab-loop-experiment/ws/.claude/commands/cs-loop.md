# /cs-loop — {{PRODUCT_NAME}} 每日治理例行（八步迴路）

對 {{PRODUCT_NAME}} 執行一次完整的 觀測 → 提案 → 落地 → 覆盤 迴路。
治理判準以 `governance/` 三文件為準，本檔只定義步驟。

**鐵律（違反即中止）**：絕不合併任何分支或 PR、絕不修改 backlog「裁決」欄、
{{PUSH_RULE|絕不 push（同步由人統一做）}}、main 上不直改 app code、
不可逆動作（如套 migration）以《Stability_Goals.md》§2.5 硬邊界為準。

## 八步

### 1. 觀測
- 讀 `governance/` 三文件、最新 health report、backlog **全部區塊**
- 收集指標原始數據：{{KPI_DATA_SOURCES}}
- 檢查上輪落地案後續（合併了沒、驗證狀態）——供第 7、8 步用

### 2. 體檢
- 量測《Evolution_Goals.md》輸入指標；尚未可量測者**誠實標「尚不可量測」**，
  不得拿活動量冒充（生成真實性）
- 迴路操作指標（若有定義）對照黃紅線標 🟢🟡🔴
- **紅線觸發**：踩紅線 → 本輪提案必含對策案（或寫明為何無法提案）；
  迴路自身失能級紅線 → 停止本輪落地、報告顯著標記、升級人類

### 3. 提案（含去重與節流）
- **去重**：已存在（任何狀態）的提案不得重提，只能引用
- **節流**：待審 ≥ {{THROTTLE_N|10}} 案或最舊待審 ≥ {{THROTTLE_DAYS|7}} 天 →
  本輪新提案上限 1 案（僅紅線級）。**節流同樣約束人類代筆的批量追加**
- **價值鐵律**：每案必須對映 SSOT §1.3 子目標或 Evolution §1.1 輸入指標，寫進動機欄；無法對映不提
- 每案：backlog「待審」加一列（裁決欄留空）＋建 `cs-loop/issues/<ID>.md`
  （背景證據、拆解 checklist、**預期指標變化**——覆盤要用）
- 表格內字面 `|` 跳脫成 `\|`（issue 檔為一般 markdown 不用跳脫）

### 4. 自評
- 價值/風險/工作量（1-10）；觸碰不可觸碰清單者風險 ≥ 8
- 對照 Stability 六大 KPI 自查清單預檢

### 5. 寫報告（治理產物直推 main）
- `cs-loop/health-reports/health-YYYY-MM-DD.md`：指標表（含尚不可量測標註）＋
  黃紅線分析＋Gate 狀態＋提案批次＋未提案觀察＋覆盤段
- 連同 backlog 新增列、issue 檔一起 commit

### 6. 落地（絕不合併）
- 僅對「已核准待落地」案：開 `land/<ID>` 分支，依 issue checklist 逐項實作勾 `[x]`
  （做不完留 `[ ]` 註明原因）；build／測試通過＋通過落地自查才 commit
- {{LANDING_LIMIT|每日至多落地一案；同時間只允許一個未合併的 land 分支}}
- 停在分支{{OR_OPEN_PR|（azdo 模式：push 分支並開 PR）}}。合併是人類的事（Gate 2）

### 7. 回寫
- 已被人合併的案：backlog 搬「已落地」、CHANGELOG 補一筆
  （動機—改動—核准人—預期指標）、issue 檔落地記錄段
- {{TICKET_WRITEBACK|外部票務系統回寫（comment＋transition）}}

### 8. 覆盤
- 對已落地 ≥ 1 天的案：比對**實際指標變化 vs 提案預期**，結果寫回 issue 檔
  （`覆盤：符合預期／偏離＋原因`）與報告覆盤段
- **判準偏差統計**：比對本輪人類裁決 vs 提案時的自評預判（高分被退、低分被核准
  即偏差），記入報告「迴路健康」段並跨輪累積；同型偏差 ≥ 3 次 → 自動開一筆
  判準修訂提案進待審（框架規則見 FRAMEWORK.md §7）
- 惡化觸紅線 → 開回滾／修正提案進待審並升級人類（不自行回滾 code）
