# Day 26：Claude 查因、修復與回歸結果

## 決定

ThreadPool starvation 已具備取代 OOM 主案例的實證。建議採「CPU 正常，服務卻卡住了，Claude 能查出為什麼嗎？」。故事從低 CPU 與慢請求的矛盾開始，經 Claude 查指標、堆疊與程式，走到兩次修法和功能回歸。既有 OOM 實驗保留為延伸，不刪原件。

本報告完成實驗選題比較；正文與封面尚未替換。這是同一訂單背景的新教學故障，不是作者當年公司事故的重建。

## Claude 真正做了什麼

- A：新 session，僅使用唯讀 MCP。經 gcx 查本機 Grafana 的 runtime 指標與 Log，讀指定程式、需求與同版堆疊。沒有提供修正版或比較報告。
- B1：另一個 session 依診斷將同步等待改成 await，保留 500ms 模擬查詢。模型也指出原有讀取、判斷、更新不具原子性，但第一版沒有修它。
- 外部驗證：不同訂單的負載恢復正常；追加的同單 16 併發卻產生 16 次狀態轉換與 16 筆通知。因此第一版未接受。
- B2：把上述失敗交回 Claude。它在 OrderStore 新增 TryCancel，500ms 非同步等待後，鎖內重新讀取、判斷並更新；只有真正轉換的那次排入通知。
- 外部固定腳本再驗兩輪，原有 11 項加同單 2 項全部通過。另核對同單 16 個回應全部 HTTP 200，不只是計數剛好等於一。

故障注入、工具介面、負載與驗收程式由備稿流程準備；診斷卡、B1/B2 程式修改確實由 Claude 產生。不能把事前準備寫成 Claude 自行開發完成。

## 診斷哪些可信，哪些仍需校正

最強依據是三者相符：pending 長時間累積、執行緒逐步增加、堆疊停在 CustomerHistory.Prepare 的同步等待；程式對應 FetchAsync().GetAwaiter().GetResult()。改為 await 後相同負載改善，是修復側的支持。

不能照抄模型全部結論：

- DOTNET_PROCESSOR_COUNT=2 只是 runtime 提示，不是 OS 兩核心配額；A3 寫「2 核上限約 200%」不適用這個環境。
- Heap 小、沒 OOM Log，不足以完全排除 GC pause；未收集完整 GC 暫停證據。鎖內有同步寫檔，也不能僅靠閱讀就宣稱所有鎖競爭已排除。
- A3 的「排空後大量完成導致 heap 增長」是推論，不是經物件分析證實的原因。
- 修後 pending 仍短暫達 72／56；驗收不是永遠為零，而是等待不再持續堆積、請求完成且功能正確。
- 尚未查明 WinError 10054 的直接來源，不把同步等待當成每種連線錯誤的已證實機制。
- 原有 read/decide/write 競態在 B1 更高併發下被驗到；不能寫成 await 憑空創造了這項缺陷。

## 工具就緒也經過修正

A1 的堆疊輸出太大，模型沒有完整讀到。A2 補分頁與時間範圍查詢，但共享重放標籤混入前一次資料；其診斷另有不合法時間文字，原件保留。A3 改用每輪獨立 job／service 標籤，七次觀測查詢皆限定該輪。它讀了堆疊前 120/843 行，足以取得多條阻塞鏈，不能宣稱讀完全部。

Grafana 裡是故障基線原始資料的時間平移重放，非 Claude 在壓測當下即時觀察。堆疊來自同版另一輪診斷取樣，不拿來與計時輪混成同一次。A3 的一秒查詢峰值與原始 100ms 取樣峰值可能不同。

## 接 後續 的依據

基線計時輪的 63 筆客戶端失敗，收尾時 384 張負載訂單仍全部完成取消與通知；另一輪含堆疊擷取的診斷輪卻只有 382 張完成。這支持「收到失敗不能直接決定重試」，不支持「所有逾時都已完成」。下一篇必須逐筆核對完成證據與安全补做條件。

## 為什麼比 OOM 更適合本次 Day 26

| 面向 | 保留 OOM | 採 ThreadPool starvation |
|---|---|---|
| 起手的矛盾 | 記憶體增加與保留物件 | CPU 不忙，請求卻排隊，更貼近作者提到的困惑 |
| Claude 參與 | 已有查因與修改實跑 | 新增唯讀查詢、堆疊核對、兩版實際修法 |
| 工程轉折 | 限制保留與同負載回歸 | 修快後功能仍錯，第二版才通過 |
| 接 後續 | 需另轉到安全重試 | 客戶端失敗與後端完成的落差直接接棒 |
| 閱讀代價 | 記憶體池比喻容易 | 需用簡短圖解釋「等待也占住工作者」，正文不可塞滿 runtime 數字 |

推薦 ThreadPool；不換算名次、冠軍機率或未執行的評審分數。
